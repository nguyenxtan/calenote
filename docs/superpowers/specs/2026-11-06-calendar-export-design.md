# Owner-authenticated calendar download

Approved scope: area 5.1 of `artifacts/diagnostics/product-next-20261104/claude-burst-calendar-design.md`. This is a one-time download, not synchronization. No provider calls, migration, deployment or secrets are needed for export.

`GET /api/calendar/export.ics` authenticates only the existing session cookie. A query parameter or Authorization header cannot authenticate it. The store repeats the live session fence in both source queries, checks it before and after decryption, and authorizes the final audit insert against the session again. All HTTP responses, including failures, must carry `Cache-Control: no-store` and `Vary: Cookie` through the router.

The logical projection uses personal workspaces with the owner's OWNER membership, the owner's bot connection, and an exact chat/workspace follow-through fence. Standalone reminders use `reminder-<root public id>@calenote`. Follow-through roots use their current reminder's time/title and the root's stable UID; intermediate runs are excluded. Legacy and canonical finite series use `series-<series public id>-<occurrence index>@calenote`, one event per materialized occurrence with no RRULE. Advance groups produce one `series-<series public id>@calenote` event using canonical resolved Gregorian `eventDate` and optional `eventTime`, regardless of original lunar provenance. Missing or foreign-bound canonical metadata is skipped rather than guessed. Notes and notification alarms are excluded; title and location are exported.

Timed values use UTC. Date-only actual event values use `DTSTART;VALUE=DATE`. For standalone reminders and ordinary finite occurrences, cancellation maps to `STATUS:CANCELLED`; other states map to `CONFIRMED`. An advance group's actual event is `CANCELLED` only when its canonical series is `CANCELLED`; stopping or cancelling individual notification work leaves an active series' actual event `CONFIRMED`. The current source timestamp determines deterministic DTSTAMP/LAST-MODIFIED; for advance groups it is the maximum of the series and all owned member reminders, their current heads and follow-through items. `SEQUENCE` is elapsed whole seconds from root creation, clamped to RFC INTEGER's maximum 2147483647. No current wall-clock timestamp enters the calendar payload. Re-exporting an unchanged projection is byte-identical.

RFC verification: [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545.html), §§3.1, 3.3.4–5, 3.3.8, 3.3.11, 3.6.1, 3.8.4.7 and 3.8.7. Content lines use CRLF; each physical line is at most 75 UTF-8 octets with code-point-preserving space continuation. TEXT escapes backslash, newline, comma and semicolon. Other control characters are stripped. UID and date/time values are validated rather than accepted as raw properties.

The window is now minus 30 days through now plus 400 days, inclusive. The final order is upcoming events earliest first, then recent past events latest first, with UID as a deterministic tie-breaker. Export includes at most 300 complete VEVENTs and 1 MiB. Each of normal and advance-group source scans reads at most 302 logical rows and decrypts at most 301. A sentinel row marks the projection partial. Advance dates are encrypted and cannot be globally ordered by actual event date in SQL; within a bounded group scan, output uses actual event dates. If a source cap is exceeded, the file is explicitly partial and does not promise the globally nearest 300 advance groups. No missing event may be inferred deleted from this bounded projection.

`X-Calenote-Export-Truncated`, `X-Calenote-Export-Skipped` and `X-Calenote-Export-Events` report the resulting file. Corrupt rows increment the skipped count once per logical event. Deliberate rows outside the time window are not corrupt and do not increment skipped. Export allows six owner requests per minute through the existing HMAC rate-limit service. Each successful response has a content-free `CALENDAR_EXPORTED` audit row; plaintext is neither logged nor persisted.

Settings UI fetches the blob with session credentials and no cache. It shows partial/skipped counts and the fixed wording “Tải một lần. Lịch của bạn sẽ không tự cập nhật; hãy tải lại nếu có thay đổi.” It explains that clients handle re-import/cancellation differently. Owner changes remount the request scope and abort its request; late old-owner responses cannot create a download.

The internal `readForSyncAuthorizedOwner(ownerId, now)` method reuses the same owner projection for background sync. Its caller must already hold the actual ACTIVE sync-connection lease for that owner. It has no HTTP owner-selector route and accepts no fabricated session principal. Sync code must retain partial/skipped metadata and must not infer remote deletion from absence.

Known semantics: standalone/ordinary finite events represent reminder times, while advance groups represent actual event times. Only canonical whole-series cancellation cancels an advance group's actual event; individual alert cancellation cannot remove that event in a sync consumer. Ordinary reminder cancellation can reflect stopped notification work rather than a cancelled real-world appointment, and the UI describes these as reminders. No calendar-client re-import or removal guarantee is made.
