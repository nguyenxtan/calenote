# Canonical series controls — completion of the finite recurrence workflow

## Why this is part of the slice

The Task2 real service test confirmed that canonical weekly/monthly series save correctly, but `D1SeriesStore.listWeb()` intentionally hides contract_version2 rows via legacyContractGuard. The former assumption that the legacy panel could list/cancel these series was wrong. Preserve that guard. Add a selected canonical reader and cancellation path, including for already supported canonical daily/advance series. Ordinary design decisions are delegated by the user's request to implement and cross-review; source work only, no production authority.

## API and UI

- A separate authenticated same-origin `/api/v2/reminder-series` GET/POST path; legacy `/api/reminder-series` remains unchanged.
- GET returns at most10owned canonical series per page/view, with safe public IDs, decrypted owned title/calendar details and up to30actual occurrence statuses/times. Use current canonical companion decryption/protocol helpers; do not run the legacy payload decoder against successor bytes. No decrypted content in logs, no credential/provider/private identity output. No external/provider call.
- POST cancels remaining occurrences using strict `{publicId,expectedRevision}` input, selected runtime capability and authenticated unrevoked/unexpired session, owner/personal-workspace/membership fences, revision CAS and durable audit. Public ID is not authority. Define clear NOT_FOUND/CONFLICT and idempotent already-cancelled outcomes.
- Cancellation is a bounded atomic D1 batch with a fresh unique marker and an audit proving the CAS winner; no partial per-child HTTP loop. Do not touch protected proposals, confirmation previews or conversation ownership. `reminder_series` status/revision can change under its owned authorization; proposal rows remain the creation lineage.
- Cancel only unacquired PENDING/CLAIMED/RETRYABLE reminders and their PENDING/RETRYABLE deliveries, including current snoozed/rescheduled descendants of series tasks. Preserve acquired SENDING/SENT/UNCERTAIN (and existing FAILED fences); do not claim that sent/in-flight messages were recalled. Stop OPEN follow-through/future follow-ups consistently. Preserve completed/history/audit.
- Both authority and child mutations must recheck owner. Concurrent/repeated cancels must not repeat unrelated updates or affect another series/owner. Missing/corrupt companion metadata fails closed. No trigger weakening or new migration is expected.
- Add a canonical series panel to the existing owned Reminders screen. Show exact dates/statuses and a local explicit confirmation step before POST. Use actual result/readback, disable duplicate submissions, retain a clear error on stale/unknown results and require reload before an uncertain retry. Clear owner data on unauthorized/session change and ignore stale late responses. No optimistic claim of cancellation.
- Read local Next16 guidance before UI edits. Preserve existing UI patterns and accessibility; no new dependency, scope-wide redesign or global Queue change.

## Root integration rulings and evidence

Canonical controls keep owner authorization after a bot disconnects: an authenticated owner can still stop their own outstanding work. The list is bounded to ten source series per page, ordered with canonically ACTIVE series before CANCELLED series, then newest creation time and public ID. Current snoozed/rescheduled heads and planned follow-ups keep the group active and visible even after original occurrences finish. Root tests enforce membership revocation, FAILED-delivery parity with individual cancellation, transaction-marker-scoped delivery changes, auth403 clearing and truthful refresh failure copy. Real Workerd/D1 with all migrations exposed trigger-inclusive meta.changes; affected tasks are pre-marked and counted from actual post-state, not that counter. Source scope verified by local tests, not production or provider delivery.

## 2026-11-06 review hardening

GET now returns `hasMore`, `nextCursor` and a per-page `skipped` integrity count alongside the bounded series array. The keyset cursor contains a validated sort rank, creation timestamp and public ID; it is a read selector, never owner/session authority. The existing live session and personal-workspace OWNER fences apply to every page. Selection reads eleven rows and examines ten; its next cursor comes from the tenth source row even when that row is skipped. Thus an all-corrupt page cannot hide later healthy rows or trap navigation. Per-row canonical binding, decryption, schema and invalid timestamp failures are excluded and counted; SQL failures still fail the request. Concurrent cancellation can move a series between sort groups, so pagination is not a transactional snapshot; refreshing restarts the currently selected page. No absence implies cancellation.

The panel replaces each page rather than accumulating an unbounded list, exposes previous/next navigation and skipped counts, and blocks stale mutation controls after failed reloads. Owner changes remount the page state, revoke pending requests during commit, and prevent a late old-owner401 from invalidating the new session. The generic API client keeps its path restriction and permits only a separately validated canonical-series cursor on the exact GET endpoint.

Pre-0014 canonical reminders can be untracked: migration0014 deliberately does not backfill existing rows. A preserved SENDING delivery can later receive a known quota rejection and become RETRYABLE. Retry acquisition now checks canonical cancellation inside the ownership mutation and atomically settles the reminder/delivery to CANCELLED with a content-free audit instead of increasing its attempt count. Tracked current descendants use their owned root lineage. Only RETRYABLE work is newly settled; already acquired SENDING/SENT/UNCERTAIN outcomes keep their existing authority and cannot be recalled. Tests reproduce the former untracked OWNED retry and tracked NOOP, and preserve successful settlement after cancellation.

Follow-through/export semantics were checked without changing the source model: STOP cancels pending reminder work but preserves SENT history. A standalone export represents the current reminder head, so stopping a pending follow-up cancels that exported reminder while the sent original remains in history. Advance groups represent the actual event and remain CONFIRMED until canonical whole-series cancellation. No new source-event cancellation authority was added.
